# procedure-runner-ux

Objective: a person runs the human steps of a procedure from a standalone console HTML (emailed, opened from any folder) with SaaS-like ease; the domain owner's agent turns the saved HTML into a changeset. Branches: `session/runner-ux-core` (runner + MCP, PR A), `session/runner-ux-procs` (procedures + CI gate, PR C), `session/runner-ux-console` (console UX, PR B, stacked on A). Delivery: PRs to `main`; merging is left to the maintainer (merge = release). Runner: vitest (`node node_modules/vitest/vitest.mjs run <file>` in `iNNfo/packages/nn-core` / `iNNfo/packages/nn-mcp`), `node --test` for scripts, Python Playwright for the UI.

## Specs

- **S1** - Flow agreed by the user (2026-11-23), verbatim: "1. Se genera la consola HTML. 2. Se envía, por ejemplo, por correo al destinatario. 3. El destinatario la descarga y ejecuta las ejecuciones que considere necesarias. 4. Guarda el fichero HTML y lo adjunta como adjunto a un correo. 5. El dueño del repo, el dueño del dominio, lo recibe y, a través del agente, actualiza los modelos a través de un changeset." The console stays a standalone file with no server as the primary path: "me gustaría que se pudiera mandar la consola por correo electrónico y ejecutarse, por ejemplo, desde la carpeta en la que la ha descargado el receptor".
- **S2** - Engine and agent steps never run in the browser; the console says so: "Este paso lo ejecuta el sistema cuando devuelvas tu respuesta".
- **S3** - SaaS-like UX: "que, para el usuario, sea intuitivo, como si estuviera usando una aplicación SaaS, y pudiera ejecutar la ejecución de un procedimiento con las menores fricciones posibles".
- **S4** - Bug: `procedure_record` MCP schema does not expose `request`, so an agent cannot consume a console Step Request (found by simulation, 2026-11-23).
- **S5** - Bug: a new run scaffolds `Example Step Run`, `Example Run Artifact`, `Example Input`, `Example Step Request` placeholder rows (`<string>` values; the request is a fake pending `start`).
- **S6** - Bug: the console shows `{slot}` placeholders unresolved (decision text, command, artifact links) and emits Step Requests with `base_seq: 0` instead of the run seq; the downloaded changeset is named after the folder, not the `workspace_id`.
- **S7** - The owner's agent turns a saved console HTML (its `nn-drafts` slot) into a changeset with one tool call, instead of reading the slot by hand.
- **S8** - A run can be requested from the console: a slot form creates a `start` request the runner consumes.
- **S9** - Console UX (user: "todos tus descubrimientos y propuestas me parecen muy acertados"): optimistic advance with the in-browser fold; one-click "save response"; "your turn" inbox first; decision buttons per branch with a reason; input artifacts embedded in the export; undo before sending; engine/agent steps labelled as run by the system with "copy instruction for the agent"; closed-run summary; technical details collapsed, short hashes; graph labels without overlap; no horizontal scroll at phone width; run filters.
- **S10** - Every shipped procedure is runnable (`procedureGraph` reports no `MISSING_SLUG` / `UNKNOWN_NEXT`), enforced by a CI gate; iNNtake's `import_and_transcribe_audio` becomes a real engine procedure; coNNtent decisions become explicit branches.
- **S11** - The simulated scenario becomes an end-to-end Playwright regression: recipient opens the console from another folder, decides, saves; the agent imports it and the run closes.
