## Specs

### S1 — `blueprint.json` beside `spec_NN.md`

Every published blueprint declares, in its own folder, exactly:

```json
{ "name": "<folder name>", "version": "V_x-y-z", "format_version": "V_x-y-z", "distribution_url": "<fetchable base URL>" }
```

- `version` is the unit's own version, identical to `blueprint_version` in that folder's `spec_NN.md` (D3).
- `format_version` is the iNNfo format the blueprint is written against, identical to `spec_version` in `spec_NN.md`.
- `distribution_url` is the **mutable, fetchable base URL of that published blueprint directory** — the address a client resolves `<distribution_url>/blueprint.json` and `<distribution_url>/versions.json` from, and whose ref segment names the commit to verify (C3).
- A blueprint whose `blueprint.json` disagrees with its `spec_NN.md`, or with the catalog's `adopted`, is a test failure naming both values. A second declaration that enforces nothing is the defect this plan exists to stop (D8).

### S2 — `versions.json` at the publisher's `distribution_url`

```json
{ "versions": [ { "version": "V_x-y-z", "tag": "<tag>", "commit": "<40-hex sha>" } ] }
```

- Publisher-owned, generated by the publisher's own release pipeline. The channel never carries versions (C3, D4).
- The client treats the list as a **hint**: it picks the highest version it can parse, then verifies the commit it names by fetching that commit's tree and comparing the `blueprint.json` version found there. A branch, a `latest` pointer and a tag list are never authority (C3).
- The generator for this repository's own release pipeline is `scripts/release/*`, owned by another session (brief "Non-goals"). This session builds and proves the client contract; it does not edit that pipeline.

### S3 — the installer records provenance

`installBlueprintAtCommit` records, for the installed copy: resolved `version`, resolved `tag`, resolved `commit` (40-hex sha), and `distribution_url` read from the installed copy's `blueprint.json` (`null` when the unit ships none). The record is written to `<blueprints_dir>/.blueprint-lock.json` (S7) — beside the installed copy, inside the directory that holds it.

- `commit` is always a sha. Today `bootstrap-state.json` carries `commit: "blueprints-v0.97.0"` for six blueprints: a tag is not a commit, and that is a bug this phase stops producing.

### S4 — install path is `<domain>/<blueprints_dir>/<name>/`

- No `<version>` segment (C4). A document's `blueprint_version` is audit metadata, not a resolution key; after an update a document authored against an older version keeps reporting `blueprint-version-mismatch` as today.
- `update` replaces that folder in place — it never adds a sibling and never merges stale files into the new layer.
- The pre-existing flat `<name>.md` duplicate (plan §2.5 defect 3) is out of P1's scope and is left untouched.

### S5 — `status` and `update` read provenance from the installed unit, never from a catalog

For every blueprint, the verdict is computed from the lock entry (S7) plus one fetch of `<distribution_url>/versions.json`:

| outcome | when |
|---|---|
| `current` | installed version equals the highest verifiable published version |
| `update-available` | a higher verifiable version exists; `status` prints it and the command that installs it |
| `unknown` | no lock entry, or a lock entry with no `distribution_url` — a unit installed before this change (A4). Never `current` |
| `unreachable` | the fetch failed; the message names the URL and the error (A3) |
| `unverifiable` | `versions.json` was fetched but the commit it names could not be verified |
| `no-versions` | `versions.json` is absent or empty; the message names the URL |

- Silence is a bug: there is no fallback to "up to date" (P1 constraint 3).
- The check is not a boot dependency (constraint 1): it runs only on an explicit `status` / `update`. No load path fetches.
- A detected update is proposed, never applied (constraint 2): `status` only reports; `update` is explicit and replaces only the managed folder, never the user's content. Refusing on local modification is P3.
- `update --blueprint <name>` installs the commit resolved from `versions.json`, not a catalog `release_tag`.

### S6 — `blueprint_version` is required at load (C2)

A level-2 or level-3 document that declares no `blueprint_version` is refused at load, and the refusal names the file and the missing field. Levels 0 and 1 are exempt: they declare `spec_version` and are not instances of a blueprint.

Measured cost of this rule in this repository: 33 core procedure documents and the `workspace` blueprint declare none, so they must gain the field or the engine stops loading them.

### S7 — the managed layer is committed with the domain, locked by `<blueprints_dir>/.blueprint-lock.json` (C5)

```json
{ "format_version": 1, "blueprints": { "<name>": { "version", "tag", "commit", "distribution_url", "digests": { "<relpath>": "<sha256>" } } } }
```

- It lives inside the domain, so it is committed with the domain and a clone on a machine with no network still reads.
- Digests are recorded now (C5); refusing an update whose digest shows local modification is P3 and is not built here.

### Acceptance

- A1 a blueprint installed from an arbitrary public repository reports `current`
- A2 a version bump at that URL is detected and applied
- A3 an unreachable URL fails loudly, naming it
- A4 a unit installed before this change reports `unknown`, never a false `current`
- A5 the check is not a boot dependency
- A6 a detected update is proposed, never applied over the user's content
- A7 every failure is a named outcome; "up to date" is never a fallback
- A8 a document with no `blueprint_version` is refused at load (C2)
- A9 a domain cloned with no network still reads (C5)
