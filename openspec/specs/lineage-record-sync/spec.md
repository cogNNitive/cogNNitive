# lineage-record-sync Specification

## Purpose

Option B: the cogNNitive lineage record stays. Its view sections are one innfo-core projection over the parsed workspace; its journal is append-only; hand-authored blocks pass through.

## Requirements

### Requirement: View sections come from one innfo-core projection

`# NN Sources`, `# NN ModelRecords`, and `# NN Artifacts` MUST be regenerated by exactly one innfo-core projection function that takes the parsed workspace (plus a filesystem snapshot) and returns the view sections. Node roles MUST come from `nn-naming-contract`: a file with a co-located sidecar is a Source, a `knowledge` document is a ModelRecord, and a non-`_NN.md` file with role `artifact` is an Artifact node only if it is a timestamped family member or declares upstream `sources`; a hand-written markdown file with neither is not projected into the record. Folder names MUST NOT decide roles. Sidecars, the record itself, and `staging/` MUST NOT appear as nodes. The filesystem snapshot reads `md`, `csv`, `json`, `html`, and `htm` files as text and skips binaries (their sidecars represent them). One `extractDeclaredCitations` function MUST serve every citation site of the projection. `nn-trannsform` MUST consume the projection through the generated esbuild mirror and MUST NOT contain a second implementation.

#### Scenario: Projection is deterministic
- GIVEN a sample workspace
- WHEN the projection runs twice with no change
- THEN both outputs are byte-identical

#### Scenario: Role follows the sidecar, not the folder
- GIVEN `artifacts/Market_20261002T101500Z.md` first without and then with a co-located sidecar
- WHEN the projection runs each time
- THEN the file appears under `# NN Artifacts` first and under `# NN Sources` after

#### Scenario: Loose hand-written markdown is not a node
- GIVEN `artifacts/notes.md` that is unsuffixed, has no sidecar, and declares no `sources`
- WHEN the projection runs
- THEN it appears in no view section

#### Scenario: Suffixed or upstream-declaring file is an Artifact
- GIVEN `artifacts/summary_20261002T101500Z.md` without `sources`, and `artifacts/memo.md` with frontmatter `sources`
- WHEN the projection runs
- THEN both appear under `# NN Artifacts`

#### Scenario: Sidecars and staging are not nodes
- GIVEN a workspace with sidecars and a file in `staging/`
- WHEN the projection runs
- THEN none of them appears in any view section

#### Scenario: Mirror stays in sync
- GIVEN the generated mirror committed under `skills/nn-trannsform/`
- WHEN the generator runs in a clean checkout and in a session worktree
- THEN the output is byte-identical to the committed file (paths normalized)

### Requirement: The record is a single living `_cogNNitive_NN.md` file

The lineage record MUST be named `<project>_cogNNitive_NN.md` (satisfying the `nn-naming-contract` invariant) and MUST be updated in place. It MUST be exempt from write-once (see `write-once-artifacts`). The `cogNNitive` record fields `archive_path` and `version` MUST follow `lineage-version-status`.

#### Scenario: Name satisfies the invariant
- GIVEN a new record
- WHEN created
- THEN its stem ends with `_cogNNitive`

#### Scenario: Update in place
- GIVEN an existing record
- WHEN `--lineage` runs after a change
- THEN the same path is rewritten and no second record exists

### Requirement: Consoles and artifacts appear with real upstream lineage

A console whose `innfo-model.meta.sources` is non-empty MUST appear in `# NN Artifacts` with those citations as its upstream lineage. An artifact MUST NOT get an empty `derived_from` solely because the generator could not scrape it.

#### Scenario: Console lineage is populated
- GIVEN a sample console embedding `innfo-model.meta.sources` with one citation
- WHEN the record is regenerated
- THEN the console entry in `# NN Artifacts` lists that citation as upstream

### Requirement: View fields are typed `citation`

The `derived_from` view field in the cogNNitive bluepriNNt (Sources, ModelRecords, Artifacts) MUST be typed `citation`, not `reference`, because it holds citations. Fields the projection does not write (`derived_from_inputs`, `generated_by`, and the others listed in `lineage-bluepriNNts-docs`) are deleted, not retyped.

#### Scenario: No dangling-reference false positive
- GIVEN a lineage record whose `ModelRecords.derived_from` holds `sources/import/a.md@## Intro`
- WHEN the cogNNitive validator runs
- THEN no dangling-reference diagnostic is reported for that field

### Requirement: Hand-authored blocks pass through

Regeneration MUST preserve every block that is not a view section or a journal entry, including `## NN External Watch Roots`, byte for byte.

#### Scenario: Watch roots preserved
- GIVEN a record with a hand-authored `## NN External Watch Roots` block
- WHEN the view sections are regenerated
- THEN that block is unchanged and `external-scanner.js` still reads it

### Requirement: Procedure runs are appended under Procedures, never replaced

`# NN Procedures` MUST use append semantics. Each pipeline operation (`--scan`, `--import-url`, `--apply`, `--lineage`) MUST append one `## NN Procedures:` entry recording `command`, `flags`, `run_at` (ISO 8601), `inputs`, and `outputs`. A refresh of the projected view sections (`# NN Sources`, `# NN ModelRecords`, `# NN Artifacts`) MUST NOT remove or rewrite existing `# NN Procedures` entries.
(Previously: the journal was named `# NN Executions` and the refreshed sections were `# NN Sources`, `# NN Models`, `# NN Artifacts`.)

#### Scenario: Scan appends a procedure entry
- GIVEN a lineage record with one existing procedure entry
- WHEN `traNNsform --scan` runs
- THEN `# NN Procedures` has two entries, the new one recording `command:: scan` and an ISO `run_at`

#### Scenario: View refresh leaves journal intact
- GIVEN a record with three `# NN Procedures` entries
- WHEN the view sections are regenerated
- THEN all three entries remain, byte-identical and in order
