# NN Critiques

## NN Critiques: Review of argon F1
target:: argon:F1
stance:: agree

The three-way split is the strongest organizing idea in either report, and it holds against the corpus. Requirement 4 (spec.md:50-53) does demand resolution for archived elements, so relocating files alone cannot stop `readLineageSnapshot` (fs-snapshot.ts:33-38) from reading them: that walker prunes only `isExcludedPath` (fs-snapshot.ts:22), and any cold zone that is not literally named `archive`/`staging` (contract.ts:192-196) is still walked. The claim that `closed: true` already exists with no consumer filtering it is confirmed: `isConsoleModel` (contract.ts:331-355) tests only `isExcludedPath`, role, root-`sources` and blueprint nature, never the `closed` frontmatter key; `listKnowledge` (list-read.ts:106-121) likewise returns every index entry. Two nuances worth adding for phase 3. First, "naming" is a code change, not just a spec change: `closed` is a frontmatter key with only one consumer, `isModelClosed` (writePolicy.ts:45-47), and the console/discovery/listing predicates would each need a new parameter, so the effort is low but non-zero and must be sequenced after the write path. Second, the third sub-problem is smaller than stated in one respect: `changes/` growth is bounded by changeset count, not by element count, so a 2,000-row compact document is a document-size and console-payload problem, not necessarily a change-log problem. Both reports should keep that distinction crisp.

## NN Critiques: Review of argon F2
target:: argon:F2
stance:: agree

All four sub-claims check out, and the first is decisive. `parsePlacement` (storage.ts:58-105) accepts only kebab-case literals, one `{slug}`, and an optional leading `{container}`, and it rejects `archive` outright through `RESERVED_LITERALS` (storage.ts:39, 93) — so the derived cold placement in Requirement 5 (spec.md:67) cannot even be expressed as a `placement::` value, it must be a second, undeclared path scheme that no storage validator knows about. The `{container}` point is also correct at the validation level: `validateStorage` expands `{container}` by taking the container's own expanded folder up to its `slugIndex` (storage.ts:291-301), so moving an archived parent instance out of that folder changes the expansion of every descendant template that starts with `{container}/`. The private-run-output point is the one I would push hardest in consolidation, and I would make it sharper than argon does: execution spec.md:279 and private-run-outputs spec.md:28 both require the `Run Artifact` row's `value` to be "that domain-relative path", and the row lives inside the very run model being moved. `update_field` cannot fix the stored path because close_model refuses every write (changes spec.md:187), so the path is permanently wrong rather than merely stale. One small correction to argon's framing: `instanceFileName` (contract.ts:77-79) makes the file name follow the folder slug, and a cold folder such as `archive/2026-11` would produce an instance name derived from the period, not from the instance — a concrete naming-invariant break that `checkInstanceName` (contract.ts:82-89) would then report. That strengthens F2 rather than weakening it.

## NN Critiques: Review of argon F3
target:: argon:F3
stance:: agree

This is the finding I would make the centrepiece of the phase-3 verdict, because it finds a self-contradiction inside the proposal rather than a conflict with something external. Requirement 2 says archiving "MUST NOT require the run to accept a write after `close_model`" (spec.md:29) and Requirement 5 says the instance "MUST record the hash of its final change log" (spec.md:68); both cannot be true at once: `close_model` sets `closed: true`, and after the closing changeset every write is refused with `MODEL_CLOSED`, "in the same changeset too" (changes spec.md:187). The `evidence_sha256` consequence is the part that makes this urgent rather than cosmetic: a closed model is citable only as a hash-verified source, and the engine stamps the closed file's sha256 (changes spec.md:217), so any later byte change silently downgrades anchor checks to `EVIDENCE_SOURCE_CHANGED` (changes spec.md:137) across every changeset that cited the run. The `procedure_state` sub-claim is also verified in code: `procedureState` calls `runAttemptsOf(loadChangeLog(root).all, ...)` (procedure-state.ts:386-390), and `loadChangeLog` is `buildChangeLog(readLineageSnapshot(rootDir))` (changelog/node.ts:8-9), so moving changesets out of the walked set removes their attempt history from that read. One thing argon asserts that I would tighten: the claim that moving single-target changesets "still leaves multi-target changesets growing" (spec.md:69 keeps them in `changes/`) is correct but is a bounding argument, not a correctness one — worth keeping, but not the reason to drop Requirement 5. The unsatisfiable write is.

## NN Critiques: Review of argon F4
target:: argon:F4
stance:: partially agree

The core objection is right and the proposal itself concedes it: spec.md:9 says segment rotation "through `extract_instance` … is not yet validated against that operation's contract", and the contract document settles the question against it. `extract_instance` requires the target concept to be distributed, refuses otherwise with `EXTRACT_NOT_DISTRIBUTED`, ends the instance id with the element slug, and re-keys the moved units in the fold through `extracted_slugs` (changes spec.md:197). So a sibling segment document that is *not* a distributed instance cannot be produced by that op, and re-keying would in any case be a fold change, not an archive visibility change. Where I part with argon is sub-claim 1. The report says the element "MUST keep slugs and hierarchical ids, so every existing address resolves" (spec.md:80) contradicts D5 because "moving element `deal-1` … changes its host model id" and resolution would require scanning siblings. The scan cost is real and I agree with it; but the proposal is not incoherent here — `canonicalModelId` derives a compact model's id as a pure function of its stem (contract.ts:391-403), so a resolver could map `crm@deal-1` to a segment document deterministically if the segment stem were derivable from a stamp, and the requirement explicitly demands exactly that. The honest verdict is "unimplemented indirection that no current resolver, reference-checker or fold supports", not "violates the addressing contract". Sub-claim 3 (hierarchy, matrices and wikilinks torn apart, `unarchive` unable to reconstruct) is the strongest part of F4 and is verified: `remove_model`'s sibling guards `MOVE_LEAVES_DANGLING_REFERENCES` and `REMOVE_MODEL_HAS_DESCENDANTS` (changes spec.md:194-195) exist precisely because cutting a node out of the graph is not a local edit, and Requirement 6 names no counterpart guard.

## NN Critiques: Review of argon F5

stance:: agree

This is the right first slice, and both code claims hold. `allowedActions` returns `[]` when `run.closed` is true (procedure-state.ts:275), so a closed run is already inert for the runner; and `close_model` already stamps `closed: true` into frontmatter (changes spec.md:187, writePolicy.ts:42-47). The missing consumer is exactly where argon points: `isConsoleModel` (contract.ts:331-355) has no `closed` branch, `listKnowledge` (list-read.ts:84-123) returns the whole index, and `isModelCandidate` (contract.ts:305-312) filters on level, `parent_spec`, exclusion and role only. Step 2 — keep closed instances at their declared `placement::` — is what makes `read_knowledge` and `procedure_state` stay O(1), since both resolve through the domain index by id (`findKnowledgeFile`, spec.ts:145-176; `readRun`, procedure-state.ts:181-204), not by folder scan. My one reservation is step 1: adding `closed_at` is a *frontmatter schema addition on the writing side*, and `close_model`'s contract as written only promises `closed: true` plus "the changeset that carries it records who closed the model and when" (changes spec.md:187). `applied_at` already exists in the changeset frontmatter (changes spec.md:139-142) and is reachable through `changesetStampOf` (contract.ts:226-232), so the retention window can be evaluated without touching the model at all. I would state F5 as "no model write needed" and reserve `closed_at` for a later, deliberate schema case — otherwise the "zero new writes" claim in argon's own recommendation is contradicted by its own step 1.

## NN Critiques: Review of argon F6
target:: argon:F6
stance:: partially agree

The `write_policy` conflict is real and I verified it in code, not only in prose: `writeOperationOf` maps `rename_element`, `update_field`, `set_fields`, `update_element_text` and `move_model` to `update`, and `remove_element`/`remove_model`/`extract_instance` to `remove` (writePolicy.ts:116-134), while `writePolicyViolation` denies any operation outside the resolved allowlist (writePolicy.ts:218-231). A new `archive` op would fall into `writeOperationOf`'s `default: return null` branch — meaning "outside the policy" — unless it is deliberately classified, and spec.md:15-17 asks for the opposite of that: archive must work "whatever its concept declares", i.e. with no policy check at all. That is a genuine hole in the proposal and deserves argon's `risk:: high`. The scopes clause is also exact: a scope declaration "only keeps or tightens" (iNNfo spec:199), so an archive that ignores scope policy is a loosening in everything but name. Where I disagree is the third sub-claim's framing. Argon says Requirement 1 and Requirement 4 "exclude an archived compact element from default console views and validation passes without specifying what happens" to dependents — true, but that is an *underspecification*, not yet an established dangling-reference break, because no apply path is defined. I would phrase it as "no analogue of `MOVE_LEAVES_DANGLING_REFERENCES` exists for archive", which is precisely the shape of the gap and is already covered by argon's own recommendation (disallow element-level archival). Stance is "partially agree" only because the headline recommendation — restrict to whole distributed instances and forbid `unarchive` on `close_model` models — is stronger than the evidence requires for the *first slice*: it settles the design question by deletion, and I would rather see it recorded as an open decision (see N2).

Sub-claim 1 is the sharpest schema observation in either report and it is verified against the Level-1 spec: Concept Definition allowed properties are `slug`, `type`, `icon`, `color`, `weight`, `storage`, `container`, `placement`, `write_policy` (iNNfo spec:140-152) — there is no terminal-state vocabulary at that level, and `transitions::` lives on `select` Field Definitions instead (executions spec:91-96 for `state`, executions spec:183-188 for `request_status`). Sub-claim 3 (changeset amplification) is correct arithmetic and is the reason Requirement 3's "the pass MUST record each archival as a change" (spec.md:40) is the wrong primitive: if archival is a projection state derived from `closed: true` plus a retention window, a pass that writes nothing but a count is sufficient. I would add one point argon leaves implicit: `keep: 5` is per-concept ordering, so the retention evaluation is a property of the *listing query*, not of the instance — which removes any need for a pass at all in the first slice.

Verified end to end. `foldStoredRun` calls `loadProcedure(root, run.procedure)` (procedure-state.ts:242), and `loadProcedure` resolves a non-floor address with `resolve(root, docAddress)` and `readFile` (procedure-state.ts:92-107), returning `PROCEDURE_NOT_FOUND` when the file is not there — so the run's recorded `procedure` address is a live path dependency, not an id. `resolveProcedure` even normalises `.md` targets with `posix.normalize` (procedure-state.ts:128-129), confirming the stored form is a path. Correct, and the state machine citation is exact: `state` declares `transitions:: {"open": ["paused", "completed", "failed", "cancelled"], "completed": [], "failed": [], "cancelled": []}` (executions spec:95), all three terminal states have no outgoing edge, and transitions are enforced at apply time by the declared-transitions check that `changeset/conflicts.ts` runs for select fields (iNNfo/packages/nn-core/src/changeset/conflicts.ts:440-463). # NN Findings

## NN Findings: N1 `loadChangeLog` filters only by filename, not by directory, so "moving changesets out of changes/" is not the lever it appears to be
category:: change
impact:: high
effort:: low
risk:: low
evidence:: verified
code_ref:: iNNfo/packages/nn-core/src/changelog/load.ts:75, iNNfo/packages/nn-core/src/changelog/load.ts:87, iNNfo/packages/nn-core/src/changelog/node.ts:8
recommendation:: State that any change-log bounding requires an explicit loader or predicate change (a directory scope, not a filename convention), and drop the assumption that relocation alone reduces the log.

Neither report notices that the change-log loader is directory-blind. `isChangesetPath` (changelog/load.ts:75-81) tests only the basename: not under root `sources/`, an `_NN.md` non-sidecar name, and a stem ending in `_changes`. `parseChangesetSnapshots` then accepts every file in the snapshot that passes it (changelog/load.ts:87-94). This matters because it flips two arguments in the reports. Argon F3 sub-claim 2 and luna F5 both assume that moving changesets "leaves `changes/`" (spec.md:75) removes them from `loadChangeLog`; they are removed only because `readLineageSnapshot` prunes the *directory* (fs-snapshot.ts:22) — and the cold zone's directory name is undecided (spec.md:8), so a cold zone named anything other than `archive`/`staging` would keep those changesets in the log, and a moved changeset whose parent folder is named `archive` disappears from it. The correct statement for phase 3 is that the log's contents are a function of the walk predicate, not of being "in `changes/`", and that `loadChangeLog` is literally `buildChangeLog(readLineageSnapshot(rootDir))` (changelog/node.ts:8-9). This also means the proposal's silent oracle is `isExcludedPath`: relocation works only by making files invisible, which is precisely the mechanism Requirement 4 (spec.md:53) forbids for archived elements — an internal contradiction no report names.

## NN Findings: N2 `instanceFileName` derives the file name from the folder slug, so any period-partitioned cold folder renames the instance model
category:: change
impact:: medium
effort:: low
risk:: low
evidence:: verified
code_ref:: iNNfo/packages/nn-core/src/naming/contract.ts:72, iNNfo/packages/nn-core/src/naming/contract.ts:77, iNNfo/packages/nn-core/src/naming/contract.ts:82, openspec/changes/archive-lifecycle/specs/archive-lifecycle/spec.md:67
recommendation:: Make "the instance keeps its file name and stem" an explicit requirement of any cold-placement design, or state that cold placement is out of scope for the first slice.

Argon F2 raises the placement-determinism cost but neither report names the naming invariant. `instanceFileName(folderSlug, blueprint)` builds the instance file name from the *folder* slug (contract.ts:77-79), and `checkInstanceName` verifies a path against exactly that derived name (contract.ts:82-89). The doc comment states the rule: the name is "derived from the slug of the folder that holds it, never from the container or the concept" (contract.ts:72-76). A cold folder such as `<placement>/archive/<period>/` therefore produces an instance whose stem is derived from the period, not from the instance, unless the instance gets its own sub-folder that restores the slug. That is a second, independent reason argon F2's Requirement 5 cannot be implemented as written, and it is cheap to state as a constraint. I record it separately because it survives even if a future design solves the scan-cost and reserved-literal problems, and because it is a naming-contract question that a storage-only review would miss.
