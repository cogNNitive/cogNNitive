# Architectural Study: Consolidation and Reorganization of cogNNitive Core Blueprints

## Context and Baseline
cogNNitive currently categorizes 8 blueprints as `tier: core` (defined in `scripts/blueprint-catalog.mjs`, `manifest/source.yaml`, and `iNNfo/packages/nn-core/src/schema/canonical-registry.ts`):
1. `domaiNN` (`iNNfo/specs/bluepriNNts/domaiNN/spec_NN.md`) — 147 lines
2. `sources` (`iNNfo/specs/bluepriNNts/sources/spec_NN.md`) — 127 lines
3. `artifacts` (`iNNfo/specs/bluepriNNts/artifacts/spec_NN.md`) — 84 lines
4. `sidecar` (`iNNfo/specs/bluepriNNts/sidecar/spec_NN.md`) — 103 lines
5. `procedures` (`iNNfo/specs/bluepriNNts/procedures/spec_NN.md`) — 301 lines
6. `executions` (`iNNfo/specs/bluepriNNts/executions/spec_NN.md`) — 248 lines
7. `changes` (`iNNfo/specs/bluepriNNts/changes/spec_NN.md`) — 220 lines
8. `blank` (`iNNfo/specs/bluepriNNts/blank/spec_NN.md`) — 109 lines

## Diagnostic: Friction Points and Structural Issues

### 1. Catalog Sprawl
A standard workspace often ends up with four separate index documents at its root:
- `domaiNN_NN.md` (indexes `kNNowledge` and local `bluepriNNts`)
- `sources_NN.md` (catalog for `Source` and `Synchronization`)
- `artifacts_NN.md` (catalog for `Artifact`)
- `procedures_NN.md` (catalog for `Procedure` definitions)

In existing examples (e.g. `docs/cognitive_nn/use-cases/consulting-sales/domaiNN_NN.md`), `domaiNN_NN.md` is forced to list `sources_NN.md`, `procedures_NN.md`, and `artifacts_NN.md` as `kNNowledge` entries, creating an index of indices.

### 2. Redundancy between `sources` and `sidecar`
Imported raw files already require a co-located companion `<file>.<ext>_sidecar_NN.md` containing `sha256`, `size_bytes`, `source_format`, `normalized_at`, and `origin_uri`.
The Lineage engine (`iNNfo/packages/nn-core/src/lineage/project.ts` and `naming/contract.ts`) already assigns the `source` role dynamically to any file with a co-located sidecar ("Nothing is persisted, so there is nothing to drift").
A static `sources_NN.md` catalog merely duplicates what `_sidecar_NN.md` already asserts physically.

### 3. Artificial Split: `procedures` vs `executions`
`procedures` defines the process schema (`Procedure`, `Work`, `Tools`, `Roles`), while `executions` defines runtime execution state (`Procedure Execution`, `Step Run`, `Run Artifact`, `Input`, `Step Request`).
This splits one functional domain (Workflow/Processes) into two separate Level-2 blueprints and duplicates concepts:
- `Work` vs `Step Run`
- `Artifact` vs `Run Artifact`
- `Procedure` vs `Procedure Execution`

Since iNNfo blueprints natively support both compact concepts and distributed concepts (`storage:: distributed`, `placement:: "executions/{slug}/"`), both definition and execution can cleanly reside in a single blueprint.

### 4. Overlap with `artifacts`
The `artifacts` blueprint defines a single concept: `Artifact` (`format`, `summary`, `status`, `artifact_model`, `file_path`). However:
- Artifacts generated by procedures are tracked by `Run Artifact` in `executions`.
- Artifacts produced by mutations are tracked by `produce_artifact` in `changes`.
- Derivative write-once files (`artifacts/*_YYYYMMDDTHHmmssZ.*`) are already dynamically projected as artifacts by `Lineage`.
A separate manual catalog blueprint is largely redundant.

### 5. Misclassification of `blank`
`blank` declares a single `Content` concept. In `naming/contract.ts`, `roleOf` treats `blank` as `'knowledge'`. It has no runtime engine logic and is simply a starter template for new models, not infrastructure.

---

## The Consolidation Proposal: From 8 to 3+1 Blueprints

We propose consolidating the 8 core blueprints into **3 foundational blueprints + 1 technical companion**:

### 1. `domaiNN` (The Unified Workspace & Inventory Backbone)
- Absorbs the catalog responsibilities of `sources` and `artifacts`.
- Concepts:
  - `domaiNN`: Container settings and conventions.
  - `kNNowledge`: Directory of domain knowledge models.
  - `bluepriNNts`: Directory of local blueprint packages.
  - `synchronization` (absorbed from `sources`): Declarations for external origins synced via `nn-sources --sync`.
  - `artifacts` (absorbed from `artifacts`): Optional declaration of major deliverables/portals.
- Fine-grained source/artifact inventory is handled dynamically by `LineageProjection`, eliminating catalog sprawl.

### 2. `procedures` (Unified Process Definition & Execution Runtime)
- Merges `procedures` and `executions` into a single Level-2 specification.
- Concepts:
  - Definition Layer (Compact): `Procedure`, `Work`, `Tools`, `Roles`, RACI matrix.
  - Execution Layer (Distributed, `storage:: distributed`, `placement:: "executions/{slug}/"`): `Execution` (header), `Step Run`, `Run Artifact`, `Input`, `Step Request`.
- Preserves 100% of the FSM stepper and runner capabilities in `nn-core` and `nn-mcp`, while unifying the process model.

### 3. `changes` (The Immutable Ledger & Review Engine)
- Retained as-is.
- Serves as the immutable event-sourcing journal, mutation engine (`apply_change`), review proposal mechanism, and cryptographic evidence anchor.

### 4. `sidecar` (The Physical File Companion — Technical Satellite)
- Retained as a dedicated, lightweight blueprint.
- Governs `<file>.<ext>_sidecar_NN.md` companion files for raw binary/text files.
- Not a domain model, but an infrastructure bridge between OS files and the semantic knowledge graph.

### 5. `blank` Reclassification
- Moved from `tier: core` to `tier: starter` or `tier: free`.
