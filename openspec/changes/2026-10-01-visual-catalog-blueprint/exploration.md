# Exploration: `visual-catalog` Level-2 BluepriNNt

## Goal

Add a NEW, domain-agnostic Level-2 bluepriNNt `visual-catalog` that lets any kNNowledge (L3) model catalog "things" extracted from images, with ENFORCED traceability: catalog entry -> evidence image -> normalized source carrying original + derivative hashes. No residential/real-estate concepts.

## Current State

The repo is the `cogNNitive` monorepo on branch `dev`. Level-2 bluepriNNts live under `iNNfo/specs/bluepriNNts/<name>/spec_NN.md`; the machine catalog is `iNNfo/specs/bluepriNNts/catalog.json`; distribution pins live in `manifest/source.yaml`. A recent rename (archived: `openspec/changes/archive/2026-09-29-nn-level-nomenclature-rename/`) moved `templates/` to `bluepriNNts/`, `template_version` to `blueprint_version`, and `model` to `knowledge`; tooling now reads the new keys only.

The proposed shape (Entry / Category / Evidence + Entry×Evidence matrix + confidence/review markers + bundled ingestion SOP) is **mostly well-supported by existing primitives**, with two real gaps: (a) no L1 primitive enforces an original<->derivative hash pairing, and (b) the many-to-many "which evidence shows which entry and how" is better modeled as a Free Matrix than as per-entry fields. A large WORKS-style ingestion procedure already exists at the workspace level (`iNNfo/specs/bluepriNNts/workspace/procedures/import_and_analyze_visual_source_NN.md`) — this blueprint must not duplicate it, but can bundle a slimmer, catalog-specific SOP.

### Q2 — Skill / procedure bundling

Evidence: `openspec/specs/template-dynamic-discovery/spec.md:9-60`, `openspec/specs/template-procedures-manifest-and-discovery/spec.md:13-27`, `iNNfo/specs/bluepriNNts/video/spec_NN.md:10-19` (blueprint-declared `procedures:`), `iNNfo/specs/iNNfo_V_0-3-0_NN.md:118` (`target_blueprint`), `skills/nn-innfo/SKILL.md:9-11` + `manifest/source.yaml:25` (`blueprints: [domaiNN]` on a skill), `manifest/source.yaml:5-71` (skills live in `cogNNitive/cogNNitive-web`).

Three distinct mechanisms exist:

- **Blueprint bundles its own procedures** (canonical, in scope for this change): declare a `procedures:` array in the blueprint frontmatter, each `{id, name, path}` with a sibling file under `procedures/`. `video/spec_NN.md:10-19` is the live example; `list_blueprint_procedures` discovers them transitively to depth 10 (`template-dynamic-discovery/spec.md:30-44`, `docs/innfo/documentation/innfo-mcp.md:34`). This is the right place for the catalog ingestion SOP.
- **Skill declares it targets a blueprint**: `blueprints: [domaiNN]` in a `SKILL.md` / manifest entry (`manifest/source.yaml:25`). A skill can also declare `bundled_blueprints` (embedding spec files, `template-skill-bundling/spec.md:37-51`; used only by `nn-innfo` today: `skills/nn-innfo/SKILL.md:9-11`).
- **Blueprint declares skills it needs**: frontmatter `skills: [{name, repo, path}]` (`template-dynamic-discovery/spec.md:11`; no live `skills:` block exists in any shipped blueprint today, only `procedures:`).

**Recommendation:** the ingestion SOP belongs in the blueprint's `procedures/` array. Do NOT create a new `nn-visual-catalog` skill for the first slice — it can be added later as `blueprints: [visual-catalog]` on an existing or future skill. This keeps the change under the review budget.

### Q4 — Traceability primitives

Evidence: `iNNfo/specs/iNNfo_V_0-3-0_NN.md:114` (field type enum), `:118` (`target_blueprint`), `:129-135` (`reference`/`knowledge`/`citation` semantics), `iNNfo/specs/bluepriNNts/artifacts/spec_NN.md:66-69` (`sources:: type:: citation`), `design-presets/spec_NN.md:85-88` and `video/spec_NN.md:64-67` (`type:: image`), `sources/spec_NN.md:77-80` (`source_model:: type:: knowledge`), `typed-source-references/spec.md:46-92`, `citation-source-resolution/spec.md:9-44`, `skills/nn-trannsform/SKILL.md:128-141` (`media_file` + `media_sha256` companion), `:142-177` (frontmatter with `source_file`, `sha256`, `size_bytes`, `normalized_at`, `normalized_by`)`.

What already exists:
- `type:: image` on a field — supported and used (`design-presets`, `video`, `organization`). Main-image resolution is deterministic: first `type:: image` field declared (`iNNfo_V_0-3-0_NN.md:346`-era rule).
- `type:: citation` on a field — supported; values are `[sources/nn/<file>#<slug>, ...]`, validated by `KU_*` checks, typed onto the graph as `origin: "source"` relationships, and resolved by `resolve_sources` (`typed-source-references/spec.md:55-61`, `citation-source-resolution/spec.md:9-44`).
- `type:: knowledge` + `target_blueprint` — links another kNNowledge doc and enforces its `parent_spec` (`iNNfo_V_0-3-0_NN.md:131`). Use this if the catalog is a separate L3 document from the domain model.
- Normalized source frontmatter carries `sha256` (of the **original**) and optional `media_file` + `media_sha256` (of a companion binary) — `skills/nn-trannsform/SKILL.md:128-141`.

**Gap (must be explicit in spec/design):** there is **no L1 primitive** that asserts `sha256_original` <-> `sha256_processed` (derivative) pairing. The `src-NNN`/line-range forms are rejected (`typed-source-references/spec.md:28-44`), and citation fields point at the NORMALIZED file under `sources/nn/`, not at the original. Therefore:
- The blueprint CAN declare a `type:: citation` field (e.g. `source`) whose value is the normalized source path — this is enforceable and resolvable.
- The blueprint CANNOT, with existing primitives alone, enforce "entry -> evidence image -> normalized source -> {original hash, derivative hash}". The double-hash guarantee must be carried by (a) the bundled SOP's steps plus (b) a gate in the ingestion procedure (compare `sha256` in the normalized frontmatter against the on-disk original, and record `media_sha256` for the derivative), and OPTIONALLY (c) a small new L1/E1 capability if the maintainer wants it machine-enforced. Recommend: encode the hash discipline in the SOP for slice 1; open a separate capability only if enforcement must be validator-level.

## Proposed schema (validated shape)

Domain-agnostic; maps to the hypothesis with two refinements.

Concepts:

- **Entry** (`type:: list` or `category`) — the cataloged thing. Fields:
  - `name` (string) — **stable domain identity**, NOT derived from a filename. This must be an explicit spec requirement (motivating finding 3).
  - `category` (`type:: reference`, `target_concepts:: [Category]`).
  - `description` (`markdown_inline`).
  - `attributes` (string; structured key/value or markdown_inline) — refine in spec.
  - `status` (`select`, e.g. `[candidate, confirmed, rejected]`).
  - `tags` (string, list).
  - `evidence` / `source` (`type:: citation`) — OPTIONAL, points at `sources/nn/...` to satisfy citation resolution.
- **Category** (`type:: category`) — hierarchical taxonomy. Fields: `name` (string), `parent` (`type:: reference`, `target_concepts:: [Category]`), `description`.
- **Evidence** (`type:: list`) — the image witness. Fields:
  - `image` (`type:: image`) — the field that makes the image addressable; first `type:: image` field = main image.
  - `captured_at` (string / date).
  - `original_ref` (string) — path to the original file in `sources/import/` or `sources/original/`.
  - `source` (`type:: citation`) — the normalized source under `sources/nn/`, carrying `sha256` (original) + `media_sha256` (derivative).
  - `notes` (`markdown_inline`).

Matrix (recommended, refines hypothesis): **`Entry x Evidence` Free Matrix** (`source:: Entry`, `target:: Evidence`, `values:: [primary, visible, partial, hidden]`, `widget:: set`, and `relationship_types.evaluable_matrix: true`). Rationale: this is exactly the L1 Free Matrix primitive (`iNNfo_V_0-3-0_NN.md:260-270`, `:182-188`), solves N:M and makes dedupe expressible (two entries claiming the same evidence are visible as separate cells; the SOP dedupes).

Markers (optional): `confidence` (`widget:: scale`) and `review` (boolean/cycle), declared via `item-markers matrix` (`iNNfo_V_0-3-0_NN.md:140-156,231-250`). Keep to two, max.

Bundled SOP (`procedures/ingest_visual_catalog_NN.md`, `id: ingest-visual-catalog`): normalize -> optimize/derive (double hash: original + derivative) -> multimodal extraction -> entity resolution/dedupe -> **idempotent** upsert -> validate. Must state the exact frontmatter discipline (`source_file`, `sha256`, `size_bytes`, `normalized_at`, `normalized_by`, `media_file`, `media_sha256`) and the idempotency key (entry stable `name`, evidence `image` path/`sha256`, matrix cell key). It should reference, not duplicate, `workspace/procedures/import_and_analyze_visual_source_NN.md`.

## Risks

1. **Hash traceability is convention, not enforced.** No L1 primitive pairs original/derivative hashes; the guarantee lives in the SOP. If the maintainer wants validator-level enforcement, it is a separate L1/E1 capability and a much larger change.
2. **Duplication with the existing workspace visual SOP.** `import_and_analyze_visual_source_NN.md` already covers image ingestion; the new SOP must be catalog-specific and reference the existing one.
3. **Filename-as-identity regression.** The whole motivating bug (finding 3) returns if `name` is not pinned as a stable identity.
4. **Idempotency is not free.** The SOP must define a deterministic key; the scanner is hash-based but element upsert is not automatic.
5. **Release coupling.** Adding to `manifest/source.yaml` under `blueprints:` also affects channel/version fan-out and tag namespace; keep the change non-release-scoped (dev) and let release tooling handle pins.
6. **`spec_url` must point at `main`, not `dev`.** The repo serves canonical URLs from `cogNNitive/cogNNitive-web@main`; a `dev` URL would break resolution.
7. **Review budget.** Blueprint file + SOP + manifest + regenerated artifacts + delta specs may approach or exceed the 400-line guard; a chained/stacked split (blueprint+schema first, SOP second, docs third) may be required.

## Recommendation

Proceed with a generic `visual-catalog` blueprint using: **Entry / Category / Evidence** concepts; an **`Entry x Evidence` Free Matrix** (not per-entry evidence fields) for N:M + dedupe; `type:: image` on `Evidence.image`; `type:: citation` on `Evidence.source` and optional `Entry.source`; `confidence` + `review` markers; and a **bundled `procedures/` SOP** for idempotent ingestion with the double-hash discipline carried in the SOP (not a new L1 primitive). Do not add a new skill in the first slice. Register in `manifest/source.yaml` + regenerate catalog/samples.ts, add the `templates.md` row, and gate with the commands in Q5.

## Open decisions for the proposal question round

1. **Hash enforcement level:** SOP-only (recommended, small) vs a new L1/validator primitive that enforces original<->derivative hashes (large, separate capability)?
2. **Evidence modeling:** Free Matrix `Entry x Evidence` (recommended) vs evidence as a field on Entry? (Matrix affects dedupe semantics.)
3. **Catalog document placement:** is the catalog always a standalone L3 document linked via `type:: knowledge` + `target_blueprint: visual-catalog`, or a sibling in the same domain file? This decides whether `target_blueprint` is needed.
4. **Concept set confirmation:** exactly `Entry`, `Category`, `Evidence` — any fourth (e.g. `EvidenceSet`, `Batch`)? Naming: `Entry` vs `Item` vs `Thing`.
5. **Markers:** keep `confidence` + `review` only, or drop markers for slice 1?
6. **Sample + bundled skill:** ship a Ghostbusters-style `samples/` doc and/or an `nn-visual-catalog` skill in this change, or defer both?
7. **Review budget:** single PR, or chained slices (schema -> SOP -> docs) per the SDD review-workload guard?
8. **`blueprint_name` frontmatter:** add it (deviation) or omit it (match siblings, recommended)?
