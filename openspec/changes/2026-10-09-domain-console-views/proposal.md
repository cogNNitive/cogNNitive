# Proposal: Domain Console Views (one console, registered views)

## Intent

Backlog decision D14 is confirmed: a domaiNN has ONE self-contained `domaiNN_console.html`, generated by `scripts/export-console.mjs`, with one snapshot hash, one draft store, one shared edit modal (D13) and one changeset per export (D8/D15). Specialized consoles become views that share the bundle and the modal. Users must also be able to author **custom views for their own domaiNN** that propose changes into the same changeset. Isolated HTML in iframes cannot do that.

## Current-state gap

- `domaiNN/assets/domaiNN_console.html` is an orphan iframe shell. It has its own script, icons and color tokens, nothing references it, and it violates the console-architecture token rule.
- Runtime bugs present in every console:
  1. The Matrices tab is empty because no `#innfo-tab-matrices` panel exists.
  2. The Review count stays frozen until reload.
  3. Export is dead: `composeExport` passes a human title to `buildFeedbackFilename`.
- No view-registration API exists. `timeline.html` and `procedure_console.html` each embed the bundle as separate shells.
- The Workspace Hub (card grid plus iframe) is legacy, and the spec still requires "Level 3 consoles MUST register in the Workspace Hub".

## Scope (chained slices)

| Slice | Deliverable |
|---|---|
| S0 Cleanup | Delete `iNNfo/specs/bluepriNNts/domaiNN/assets/domaiNN_console.html`. |
| S1 Runtime fixes (test-first, jsdom) | Give Matrices its own tab panel. Re-render the Review badge and the pending text on every draft save or delete. Build the export filename from a slugified model identifier (`model_slug` per D4; core `slugify` is already bundled). Rebuild the bundle. |
| S2 View registry | A runtime extension point (`registerView`) that gives a view the shared payload, draft store and edit modal, and renders it as a tab in `domaiNN_console.html`. A registered view can still be exported standalone. Migrate `timeline.html` and `procedure_console.html` as the first views. `export-console.mjs` discovers bluepriNNt views and domaiNN custom views. |
| S3 Retire Hub legacy | Delete `workspace_hub.html`, `compile_workspace_hub_NN.md`, `_samples_nn/.../compile_workspace_hub_procedures_NN.md` and `docs/.../workspace-console-hub.md`. Update `console-architecture` and `reviewer-guide.md` to the D14 model. |

### Non-goals

- No iframe composition for editable views.
- No backwards-compat aliases, redirects or hub fallback. Legacy is deleted. Any temporary leftover carries a `legacy:<ns>/<id>` marker plus a ledger entry.
- No changes to the changeset or feedback schema beyond the filename fix.
- No migration of `model_console.html` or the document SOP console in this change. This is a candidate follow-up.

## Capabilities

### New Capabilities
- `console-view-registry`: the view registration contract, shared payload, draft store and modal access, tab mounting, standalone export, and discovery of bluepriNNt and domaiNN custom views.

### Modified Capabilities
- `console-architecture`: replace "Level 3 … register in the Workspace Hub" with "views register in the domaiNN console runtime". Single domain console per D14.
- `console-tabbed-views`: tabs come from the registry. Matrices gets its own panel.
- `innfo-console-feedback`: the export filename derives from the model slug. The draft count is live across banner, tab badge and Review panel.
- `console-hub-onboarding`: removed with the hub, since the Vue editor is retired by D13/D18 (pending OQ5).

## Approach

Keep the D14 single-artifact model. Views are JS modules registered at runtime and inlined by `export-console.mjs` next to the bundle. Shells stay layout-only and use `--innfo-*` tokens. S1 lands first and stands alone. S2 is the architectural slice and goes through design. S3 runs only after S2 replaces what the hub provided.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| User-authored view code runs with full page access | High | OQ2 is decided in design before S2 apply. |
| Inlining every model and view breaks the D14 size budget | Med | OQ4 plus a measured budget check in export. |
| The editor Consoles view depends on the hub | Med | S3 runs after S2. OQ5 is resolved first. |
| The bundle is stale after source edits | Med | Rebuild before tests. `check-integrity` catches it. |

## Rollback

Each slice is an independent commit set. Revert S3 to restore the hub files and spec, and revert S2 to drop the registry while the shells stay as they are. S0 and S1 are safe deletions and bug fixes with no dependents.

## Success Criteria

- [ ] Matrices render. The Review count updates without reload. Export downloads in the domain console and in every console.
- [ ] `timeline` and `procedure` run as tabs in `domaiNN_console.html`, and their drafts land in the single changeset.
- [ ] A sample custom view in `_samples_nn` is registered, exported and proposes a change.
- [ ] Zero references to `workspace_hub` remain. `console-shell-guard` and `check-integrity` are green.

## Open questions (proposal question round, needs maintainer review)

1. **Custom view location and discovery.** Where do custom views live in a domaiNN (for example `consoles/views/<slug>.js`), and is a manifest or naming convention what `export-console.mjs` discovers?
2. **Trust and sandboxing.** User-authored view code is inlined into an artifact that reviewers open. Should views be sandboxed, restricted to a declarative or API-only surface, or trusted as the domain owner's own code?
3. **Read-only arbitrary HTML.** May non-editing HTML (for example a static report) still be embedded, possibly in an iframe, since it never touches the changeset?
4. **Size budget (D14).** What is the maximum artifact size, and what happens when it is exceeded: warn, fail, or lazy-split?
5. **Editor Consoles view.** D13/D18 already retire the Vue `innfo-editor` (read-only until deleted). Is `console-hub-onboarding` therefore REMOVED with the hub (default assumption), or retargeted to `domaiNN_console.html` until the editor is deleted?
6. **Standalone view export.** Is this the same exporter with a view filter (one changeset scope per view), or is it out of scope for the first slice?
