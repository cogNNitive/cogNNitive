# Proposal: Domain Console Views (one console, registered views)

## Intent

Backlog decision D14 is confirmed: a domaiNN has ONE self-contained `domaiNN_console.html`, generated by `scripts/export-console.mjs`, with one snapshot hash, one draft store, one shared edit modal (D13) and one changeset per export (D8/D15). Specialized consoles become views that share the bundle and the modal. Users must also be able to author **custom views for their own domaiNN** that propose changes into the same changeset. Isolated HTML in iframes cannot do that.

## Current-state gap

- `domaiNN/assets/domaiNN_console.html` is an orphan iframe shell. It has its own script, icons and color tokens, nothing references it, and it violates the console-architecture token rule.
- Runtime bugs present in every console:
  1. The Matrices tab is empty because no `#innfo-tab-matrices` panel exists.
  2. The Review count stays frozen until reload.
  3. Export is dead: `composeExport` passes a human title to `buildFeedbackFilename`.
- No view-registration API exists. `timeline.html` and `procedure_console.html` each embed the bundle as separate shells.
- The Workspace Hub (card grid plus iframe) is legacy, and the spec still requires "Level 3 consoles MUST register in the Workspace Hub".

### Non-goals

- No iframe composition for editable views.
- No backwards-compat aliases, redirects or hub fallback. Legacy is deleted. Any temporary leftover carries a `legacy:<ns>/<id>` marker plus a ledger entry.
- No changes to the changeset or feedback schema beyond the filename fix.
- No migration of `model_console.html` or the document SOP console in this change. This is a candidate follow-up.

## Capabilities

### New Capabilities
- `console-view-registry`: the view registration contract, shared payload, draft store and modal access, tab mounting, standalone export, and discovery of bluepriNNt and domaiNN custom views.

### Modified Capabilities
- `console-architecture`: replace "Level 3 … register in the Workspace Hub" with "views register in the domaiNN console runtime". Single domain console per D14.
- `console-tabbed-views`: tabs come from the registry. Matrices gets its own panel.
- `innfo-console-feedback`: the export filename derives from the model slug. The draft count is live across banner, tab badge and Review panel.
- `console-hub-onboarding`: removed with the hub, since the Vue editor is retired by D13/D18 (OQ5 resolved).

## Approach

Keep the D14 single-artifact model. Views are JS modules registered at runtime and inlined by `export-console.mjs` next to the bundle. Shells stay layout-only and use `--innfo-*` tokens. S1 lands first and stands alone. S2 is the architectural slice and goes through design. S3 runs only after S2 replaces what the hub provided.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| User-authored view code runs with full page access | High | Trusted by decision (OQ2); the exporter lists included views in the header. |
| Inlining every model and view breaks the D14 size budget | Med | Warn 5 MB / fail 15 MB measured in export (OQ4). |
| The editor Consoles view depends on the hub | Med | S3 runs after S2. OQ5 resolved: onboarding is removed. |
| The bundle is stale after source edits | Med | Rebuild before tests. `check-integrity` catches it. |

## Rollback

Each slice is an independent commit set. Revert S3 to restore the hub files and spec, and revert S2 to drop the registry while the shells stay as they are. S0 and S1 are safe deletions and bug fixes with no dependents.

## Resolved questions (maintainer, 2026-10-09)

1. **Custom view location and discovery.** Convention over configuration: every `consoles/views/<slug>.js` in a domaiNN is discovered by `export-console.mjs`; the slug is the file name. No manifest.
2. **Trust and sandboxing.** Trusted: a custom view is the domain owner's own code, the same trust level as any repo script. No sandbox. The exporter lists the included views in the artifact header so a reviewer can see what runs. This is the only model compatible with a shared edit modal and draft store without an iframe (D13).
3. **Read-only arbitrary HTML.** Allowed. A view declared `readonly` may mount static HTML in a sandboxed `iframe srcdoc` with no access to the draft store or the changeset. D14 forbids iframes only for editable views.
4. **Size budget (D14).** The exporter measures the final HTML: warn above 5 MB, fail above 15 MB, with a breakdown (bundle / models / views). No lazy-split in this change. Thresholds live in one constant.
5. **Editor Consoles view.** `console-hub-onboarding` is REMOVED together with the hub. No retargeting, no bridge code.
6. **Standalone view export.** In scope for S2: the same exporter with a view filter (`export-console.mjs --view <id>`), producing the bundle plus that single view and a changeset scoped to it. This keeps `timeline` and `procedure` deliverable on their own after migration.
