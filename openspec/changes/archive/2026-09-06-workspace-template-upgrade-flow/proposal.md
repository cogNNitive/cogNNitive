# Proposal: Workspace Template Upgrade Flow (2026-09-06)

## Intent

A user workspace is created at time T1 pinned to a set of immutable, filename-versioned
iNNfo Level-1 specs and Level-2 templates. The canonical `cogNNitive` repository later
publishes newer template versions (a bump always creates a *new* file; the old file stays
frozen and resolvable forever). When the user resumes their workspace and runs `nn`
(`nn-preflight`), nothing today tells them a superseding template exists — the workspace
`specs/` freshness scan hashes each local file against its **own** declared canonical URL,
which never changes for an immutable pinned file.

This change gives the ecosystem a real **workspace template upgrade flow**:

1. A machine-readable **template catalog** that answers "which template versions exist,
   and which is adopted/current".
2. A deterministic, read-only **upgrade detection scan** in `nn-preflight` (Tier 3) that
   classifies every Level-3 model in a workspace against the catalog
   (`current` / `upgrade-available` / `ahead` / `unlisted`) without ever blocking normal
   work.
3. A new **`nn-upgrade` skill** that owns the consent-gated migration: detect → inform →
   backup → schema-impact analysis → migrate (repoint `parent_spec` + re-validate) →
   confirm.

This mirrors the existing architecture rule: **detection is read-only and lives in
`nn-preflight`; mutation is consent-gated and lives in a dedicated skill** — the same
seam the ecosystem already uses for components (`preflight-check.js` reports,
`nn-skills-lifecycle` mutates).

## Problem summary

| Gap today | Evidence |
| :--- | :--- |
| A pinned, immutable `parent_spec.url` is always "fresh" under the content-hash scan | `preflight-check.js` `scanWorkspaceSpecs` compares local bytes against the *same* canonical URL (`actioNN/skills/nn-preflight/scripts/preflight-check.js`) |
| No machine-readable "current version" source per template | adopted versions live in editor constants + docs tables + the bootstrap manifest; nothing answers a version query |
| "Existing L3 models are not migrated" is the documented default | `docs/innfo/documentation/specifications.md:112-113` — repointing is manual |
| No backup + re-validation ceremony before a template repoint | `innfo-mcp` `bump_version` re-versions local specs; nothing migrates a model to a *new canonical* template |

## Affected modules

| Module | Change |
| :--- | :--- |
| `iNNfo/specs/templates/` | `catalog.json` — regenerable, committed machine-readable template catalog |
| `scripts/` | `template-catalog.mjs` — generator + `--check` drift gate |
| `actioNN/skills/nn-preflight` | `scripts/upgrade-check.js` (Tier 3 scan) + `preflight-check.js` wiring + SKILL.md Tier-3 section |
| `actioNN/skills/nn-upgrade` | **new** skill: guided, consent-gated migration flow + `scripts/backup-workspace.js` |
| `docs/` | new `nn-upgrade` skill page; Tier-3 notes on the `nn-preflight` page |

## Scope

### In scope

1. **Template catalog artifact** (`iNNfo/specs/templates/catalog.json`): one JSON object;
   each canonical template name maps to its published immutable versions (from the specs
   tree) plus an `adopted` version (highest published `template_version`). Regenerated by
   a deterministic generator; `--check` fails on drift so the artifact cannot silently
   rot.
2. **Tier-3 upgrade detection** (`upgrade-check.js`, wired into `preflight-check.js` when
   `--workspace-dir` is given): discovers Level-3 models, matches each model's
   `parent_spec.url` basename against the catalog, and classifies the model. Non-mutating.
   **Never flips the exit code**: an available upgrade informs and offers; it does not
   block the session. If the catalog cannot be fetched, the scan degrades to an
   `offline` notice.
3. **SemVer gap classification**: `major` / `minor` / `patch` for the bump between the
   pinned and the adopted template version, per `defiNNe` §7. The gap kind drives how much
   migration scrutiny a model needs.
4. **`nn-upgrade` skill**: the full guided flow. Backup MUST be taken **outside** the
   workspace before any write; upgrade MUST be offered with `[a] Upgrade (Recommended) /
   [b] Continue`; mapping questions MUST only be asked when the schema diff removes,
   renames, or re-types something the model actually uses; every migrated model MUST be
   re-validated through `innfo-mcp`; a before/after report closes the flow.
5. **Backlog entry** (detailed) for local-specialization migrations — deferred, not part
   of this change.

### Out of scope

- Migrating **local specializations** (`*_spec_NN.md` authored by the user): detection
  reports them `unlisted`, migration guidance only → tracked in `openspec/backlog.md`.
- Changes to `innfo-core` / `innfo-mcp` engines (no new MCP tool in this change; schema
  diffing is done by the agent from `read_model` + template resolution).
- Publishing/distribution plumbing: version bump + manifest `commit` pin sync for the new
  skill rides the normal release flow (`nn-dev-release`); no channel/CDN work here.
- L1-only adoption tracking beyond what the template catalog inherits transitively.
- Auto-apply, scheduled checks, or any silent migration.

## Delivery

`delivery_strategy: auto`, `single-pr-default`, review budget well under 800 lines of
new engine code. TDD strict: each new script ships with its `.test.js` (plain `node`,
matching the existing `preflight-check.test.js` convention). Verification = the new
`.test.js` files + the existing `preflight-check.test.js` suite staying green.
