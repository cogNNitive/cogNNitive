# Delta Spec: manifest-governance

Scope guard: only distribution names and paths in `manifest/source.yaml` change. The skill `nn-innfo`, the iNNfo term and the `docs/innfo/` URL base are NOT renamed.

## MODIFIED Requirements

### Requirement: Core-Only Blueprint Inventory in Source Manifest

`manifest/source.yaml` and `scripts/generate-canonical-registry.mjs` (`canonical-registry.ts` in `@cognnitive/nn-core`) MUST restrict bundled `bluepriNNts` inventory to the 7 Core `bluepriNNts` (`domaiNN`, `changes`, `sidecar`, `sources`, `artifacts`, `procedures`, `blank`). Optional domain and vertical `bluepriNNts` MUST be governed through `iNNfo/specs/bluepriNNts/catalog.json` (`scripts/blueprint-catalog.mjs`) including `tier`, `access`, `embedded_skills`, and release pins.

(Previously: the registry lived in `@cognnitive/innfo-core`.)

#### Scenario: Validating core-only manifest and canonical registry inventory
- **GIVEN** `manifest/source.yaml` and `canonical-registry.ts` generated by `scripts/generate-canonical-registry.mjs`
- **WHEN** `scripts/verify.js` validates the blueprint inventory
- **THEN** all 7 Core `bluepriNNts` (`domaiNN`, `changes`, `sidecar`, `sources`, `artifacts`, `procedures`, `blank`) are present in `manifest/source.yaml` and `canonical-registry.ts`
- **AND** optional vertical `bluepriNNts` are absent from `manifest/source.yaml` and validated against `catalog.json` instead

## ADDED Requirements

### Requirement: Source inventory uses nn-prefixed distribution names and paths

From PR 3 `manifest/source.yaml` MUST declare the MCP unit as `nn-mcp` (`name`, `ref_key`); its `path` is under `iNNfo/packages/nn-mcp/` from PR 1 (the `name` stays `innfo-mcp` between PR 1 and PR 3). From PR 2 every `console_assets` entry has `ref_key: nn-console` and a `path` and file name carrying the `nn-` prefix (the console runtime sources, the `nn-ui.css` stylesheet and the `nn-console.bundle.js` bundle). Every `path:` MUST exist in the tree. The names in `source.yaml` MUST match `RELEASE_KEYS` and the release tag families, so that a release key, its manifest `ref_key` and its entry name are the same string.

#### Scenario: Names agree across release key, source and manifest
- GIVEN the release key `nn-console`
- WHEN `RELEASE_KEYS`, `manifest/source.yaml` and an assembled manifest are compared
- THEN the console entries carry `ref_key: nn-console` in the source and in the manifest

#### Scenario: Declared path missing
- GIVEN a `console_assets` entry whose `path:` still names `innfo-runtime.js` after the file was renamed
- WHEN `verify.js` runs
- THEN the inventory guard fails

### Requirement: source.yaml carries no legacy identifiers

`manifest/source.yaml` MUST NOT declare `legacy_names`, `legacy_files` or any other alias for a renamed unit. Each unit has one primary name. Retention of pins from the last published `innfo-*` manifest is handled by the transient assemble-time `PREVIOUS_PIN_RENAMES` map (see `monorepo-release-manifest`), which is code, not inventory data. The governance guard MUST fail when a legacy field appears.

#### Scenario: Legacy field rejected
- GIVEN `manifest/source.yaml` with a `legacy_files` list on a console asset
- WHEN the governance guard runs
- THEN it fails and names the field

#### Scenario: No legacy fields present
- GIVEN `manifest/source.yaml` after PR 3
- WHEN it is scanned for `legacy_names` and `legacy_files`
- THEN none is present
