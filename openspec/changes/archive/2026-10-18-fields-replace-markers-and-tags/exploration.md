# Exploration: fields-replace-markers-and-tags

Phase: sdd-explore | Store: openspec | Worktree: `session/ku-mockup` @ `3afaa90e` (main)
Backlog link: `openspec/backlog.md` item 37 (`chore/markers-review`, "possibly merge markers with tags").

## 0. Decisions taken (not re-litigated)

1. Remove the `Marker Definition` root primitive (4 -> 3: Concept, Field, Matrix); remove the reserved `item-markers matrix` and the `Markers` pseudo-concept.
2. Flag markers become tags. Valued markers become ordinary Field Definitions (multi-concept, with `widget` / `widget_config`).
3. Tags are an ordinary `select` Field (open vocabulary without `options`, closed with them), multi-valued, no color/icon/symbol; tag color = stable hash of the name onto the 12 concept color slots; `tags::` loses its special parsing.
4. Delete the `Tags` concept (domaiNN + workspace bluepriNNts).
5. Generic concept-level value inheritance (multi-valued: union; single-valued: element overrides).
6. Field Definition gains a multi-concept target (`concept:: *` or a list).
7. Console `tag:` / `tag-any:` becomes a generic `<field>:value` filter.
8. No backwards-compat aliases; published `_V_x-y-z_` spec files are write-once, so a NEW L1 file is required.

## 2. Approaches

### 2.A Where `concept:: *` / list is expanded
| Option | Pros | Cons |
|---|---|---|
| A1. At `extractBlueprintSchema` (per blueprint) | Local, simple | `*` inside `analysis` would not reach `organization` concepts when composed into `business`; two blueprints declaring `*` fields yield per-concept duplicates compared by the weak `JSON.stringify` check |
| **A2. After composition in `resolveBlueprintSchema` (recommended)** | `*` means "every concept of the effective schema", exactly the old marker semantics; global fields dedupe by canonical form; consumers (validator, `slot.ts`, `review.js fieldDefOf`) keep reading `concept.fields` unchanged | Needs a carried `globalFields` list through `BlueprintSchema` and compose; rule needed: concept-specific Field beats a `*` Field of the same name (e.g. `projects` `Task.priority` select vs a hypothetical global `priority`) |
| A3. Keep `*` unexpanded and resolve at lookup | No schema churn | Every consumer must learn `*`; console/review lose the flat (concept, field) table |

### 2.B How a Field declares multiple values
| Option | Pros | Cons |
|---|---|---|
| B1. Infer from value shape (`[a, b]`) | No new property | Single tag `tags:: urgent` is a string; inheritance (union vs override) cannot be decided from the schema |
| **B2. New explicit Field property (e.g. `multiple:: true`) (recommended)** | Union-vs-override is schema-decidable; validator can check each array member; console renders chips vs single picker | One more L1 property + metaschema entry; must decide if only `select` may be multiple |

### 2.C Declaring `tags` across blueprints
| Option | Pros | Cons |
|---|---|---|
| **C1. Every content blueprint declares one identical open-vocabulary `tags` Field (`concept:: *`, `type:: select`, `multiple:: true`, no `options`) (recommended)** | Dedupes silently under `includes`; each blueprint still "decides" (a closed list is a deliberate local override) | 10+ near-identical blocks; a closed-list override in one included blueprint collides (see Q4) |
| C2. L1 defines an implicit universal `tags` | Zero repetition | Contradicts decision 3 ("each bluepriNNt decides") |
| C3. Shared fragment blueprint included everywhere | One definition | New artifact, new `includes` edges, `base` is frozen |

### 2.D Concept-level fields: parser model
| Option | Pros | Cons |
|---|---|---|
| **D1. Generalise `conceptTags`/`rawConceptTags` into `conceptFields` + `rawConceptFields`, parsed from the leading property lines of a concept section (recommended)** | Same fidelity technique as tags; stops at first prose/heading; round-trip stays byte-identical | Text-type concepts whose prose begins with `word:: x` lines would be consumed (zero occurrences in the shipped corpus other than the `domaiNN` root); the serializer must emit a section that has ONLY concept-level fields |
| D2. Require an explicit sentinel (e.g. `## NN <Concept>` self-element) | No ambiguity | New syntax; contradicts decision 5 ("written under `# NN <Concept>`") |

### 2.E Valued-marker mapping rule
Rule proposed: symbol-only flags (no `values`, no `widget`) -> tag; anything with `widget`/`values`/numeric usage -> Field. Boundary cases: `shipped` and `review` carry `widget:: boolean` (a presence flag with labels) -> Field `boolean` widget to keep `true_label/false_label`; alternatively tag `shipped`. The `certainty` triple-usage must be settled once (Field `scale`, and rewrite the innovation `?` rows and the business 1-5 scale).

## 5. Gaps and open questions

1. **Multi-value syntax and cardinality (blocking design).** Add an explicit Field property (`multiple`)? Does `select` alone qualify? Accepted forms: only `[a, b]` (today's data) or also bare `a, b` (current docs/test)? Single value `tags:: urgent` is a string and must validate as a one-element list.
2. **Field `type` vs `widget`.** L1 `type` has no `number`/`boolean`; `scale` and `boolean` widgets imply numeric/boolean values. Add types, or keep `type:: string` and let the widget carry meaning (then `scale min/max` cannot be enforced by the validator)?
3. **Case normalization.** Tags are lowercased and trimmed by `parseTagList`; ordinary values are verbatim. Case-insensitive matching must be restated for tag fields or the console hash color / facet matching must lowercase.
4. **Closed tag vocabularies vs `includes`.** Two included blueprints declaring `tags` with different `options` raise `COMPOSITION_COLLISION`. Union semantics for `options`, or forbid closed `tags` when included, or each closed list gets its own differently-named Field.
5. **Where `*` stops.** Include `type:: text` concepts (no elements) and the reserved structural concepts (`index`, `matrices`, `Sources`, `Models` ...)? Specific-concept Field beats `*` Field of the same name (proposed).
6. **Concept-level value semantics.** Which element wins when the concept-level value is invalid for the element's concept? Is the inherited value validated against the field of the element's concept? Is an inherited value written back by mutations (no: own values only; rename/delete cascades only touch own values)? What are the exact read APIs: payload `fields` (own) vs a new `inherited` map vs effective merge?
7. **Hash.** Decide: keep a constant `markers: {}` in `computeElementHash` to preserve every existing hash, or accept one global invalidation (ledgers, open changesets, `reviewed` maps). Tags/own fields enter the hash after this change either way; inherited values must stay out.
8. **Legacy documents.** Core after the change: a stale `# NN Marker Definition` in a user-local bluepriNNt or an `item-markers matrix` table in an L3 file becomes (a) an unknown concept / ordinary matrix with a warning, or (b) a hard error. `nn-upgrade` has "no in-place migration" (import-as-source) and Flow B for blueprint version upgrades; the data conversion (markers -> tag/field values) is mechanical but must be scripted or hand-done for the 6 samples. `RESERVED_STRUCTURAL_HEADINGS` must stop treating `item-markers matrix` specially or keep rejecting it.
